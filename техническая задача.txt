# Техническое задание

## Полное исправление и доведение Pinduoduo Uzbekistan до рабочего MVP

### 1. Цель

Полностью исправить существующий репозиторий:

`toxa2210/Pinduoduo-Uzbekistan`

Не переписывать проект с нуля.

Не удалять существующую архитектуру без необходимости.

Не делать временные визуальные заглушки вместо функциональности.

Главная задача:

> Frontend должен полностью и стабильно работать с Backend API, а Backend должен иметь корректную архитектуру для локальных товаров и товаров Pinduoduo.

# 2. Главный принцип

Frontend не должен самостоятельно хранить бизнес-логику.

Frontend отвечает за:

* UI;
* состояние интерфейса;
* ввод пользователя;
* отображение данных;
* вызов API.

Backend отвечает за:

* пользователей;
* авторизацию;
* товары;
* PDD integration;
* корзины;
* цены;
* валюты;
* заказы;
* платежи;
* доставку;
* статусы;
* безопасность.

Архитектура:

```text
Frontend
    ↓
REST API
    ↓
Backend
    ├── PostgreSQL
    ├── Redis
    ├── PDD Adapter
    ├── Payment Adapter
    └── Delivery Adapter
```

# 3. Обязательное правило перед началом работы

Перед изменением кода:

1. Проверить текущую ветку `main`.
2. Создать отдельную рабочую ветку:

```text
fix/full-mvp-integration
```

3. Не удалять рабочие части проекта.
4. Не менять API без обновления frontend.
5. После каждого крупного блока запускать build/test.
6. Не использовать реальные API credentials в Git.
7. Не добавлять секреты в frontend.
8. Не делать fake-success для платежей.
9. Не использовать mock PDD data там, где уже доступен реальный backend endpoint.
10. Все ошибки должны отображаться пользователю понятным сообщением.

# 5. Полностью переписать API client

Создать единый API client.

Например:

```text
services/api/client.ts
```

Он должен автоматически:

* брать `VITE_API_URL`;
* отправлять JSON;
* добавлять Authorization;
* обрабатывать HTTP errors;
* обрабатывать timeout;
* возвращать типизированный ответ;
* не дублировать fetch logic.

Authorization:

```http
Authorization: Bearer <access_token>
```

Token хранить безопасно для текущего MVP, но архитектуру сделать так, чтобы позже можно было перейти на HttpOnly cookie.

```text

↓

↓

↓

↓

```

Frontend после login обязан использовать полученный token.

API:

```text
POST /auth/request-otp
POST /auth/verify-otp
GET  /auth/me
POST /auth/logout
```

Добавить:

* loading;
* cooldown;
* повторную отправку;
* ошибку неправильного OTP;
* expired OTP;
* logout;
* восстановление session после reload.

После reload пользователь не должен автоматически становиться anonymous, если действующая session существует.

# 55. Definition of Done

Проект считается исправленным только если выполняется всё ниже.

### Frontend

* [ ] сайт запускается;
* [ ] нет критических console errors;
* [ ] все основные кнопки работают;
* [ ] каталог работает;
* [ ] поиск работает;
* [ ] карточка товара работает;
* [ ] PDD товары отображаются при настроенном PDD API;
* [ ] login работает;
* [ ] token реально используется;
* [ ] корзина сохраняется на backend;
* [ ] reload не уничтожает корзину;
* [ ] checkout работает;
* [ ] заказ создаётся;
* [ ] payment flow работает;
* [ ] orders работают;
* [ ] ошибки отображаются корректно.

### Backend

* [ ] build проходит;
* [ ] Prisma generate проходит;
* [ ] Prisma validate проходит;
* [ ] database работает;
* [ ] Redis работает;
* [ ] auth работает;
* [ ] catalog работает;
* [ ] PDD adapter работает;
* [ ] cart работает;
* [ ] checkout работает;
* [ ] orders работают;
* [ ] payments имеют callback;
* [ ] idempotency работает;
* [ ] rate limiting работает;
* [ ] error handling унифицирован.

### PDD

При отсутствии credentials:

```text
PDD = NOT_CONFIGURED
```

При наличии credentials:

```text
PDD status = HEALTHY
```

и:

```text
search
details
categories
```

должны реально возвращать данные.

Необходимо отдельно документировать, какие операции PDD доступны предоставленному аккаунту/API, а какие пока являются неподдерживаемыми.

### CI

Последовательность:

```text
npm install
↓
prisma validate
↓
prisma generate
↓
backend build
↓
frontend build
↓
tests
```

должна проходить без ошибок.

# 57. Итоговая цель

После выполнения ТЗ пользователь должен воспринимать сайт не как демонстрационный prototype, а как настоящий работающий e-commerce MVP.

Нельзя оставлять состояние:

```text
"Кнопка есть, но пока ничего не делает"
```

или:

```text
"API есть, но frontend его не использует"
```

или:

```text
"Payment backend есть, но checkout его не вызывает"
```

или:

```text
"PDD search работает, но товар нельзя провести через cart → checkout → order"
```

Каждая основная функция должна пройти полный путь:

```text
UI
↓
API
↓
Business logic
↓
Database/provider
↓
Response
↓
UI
```

После завершения обязательно выполнить финальный аудит всего репозитория и предоставить отчёт:

```text
BUILD: PASS/FAIL
DATABASE: PASS/FAIL
AUTH: PASS/FAIL
CATALOG: PASS/FAIL
PDD: PASS/FAIL
CART: PASS/FAIL
CHECKOUT: PASS/FAIL
ORDERS: PASS/FAIL
CLICK: PASS/FAIL
PAYME: PASS/FAIL
PAYNET: PASS/FAIL
DELIVERY: PASS/FAIL
E2E: PASS/FAIL
CI: PASS/FAIL
```

А также список всех оставшихся `TODO`, `FIXME`, mock/stub участков и функций, которые требуют реальных credentials или официального доступа Pinduoduo.
